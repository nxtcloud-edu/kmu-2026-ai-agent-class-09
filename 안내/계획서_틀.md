# 계획서 틀과 예

`계획서.md`의 모든 칸을 채운다. 이 파일은 각 칸에 무엇을 쓰는지와 예를 보여 준다. 예의 일 1은 "마감 관리", 일 2는 "채용 공고 점검"이다.

## 1. 맡길 일 (2개 이상)

일마다 한 칸씩 쓴다. 일이 3개면 칸을 더한다. 일 하나의 기준은 [최종결과물.md](최종결과물.md)에 있다.

| 칸 | 쓸 것 | 예: 일 1 | 예: 일 2 |
|---|---|---|---|
| 이름 | 한 줄 | 아침 마감 브리핑 | 아침 공고 브리핑 |
| 반복하는 일 | 무엇을, 얼마나 자주 하는가 | 매일 과목별 공지에서 마감을 찾는다 | 매일 아침 채용 사이트 3곳을 본다 |
| 지금 하는 방법 | 단계와 걸리는 시간 | 공지 5곳 확인 → 메모. 하루 15분 | 검색 → 내 조건과 비교 → 메모. 하루 30분 |
| 맡길 부분 | 단계 번호 | 마감 찾기, 정리 | 검색, 비교, 메모 정리 |
| 내가 계속 할 부분 | 단계 번호 | 모호한 마감 확정 | 지원 여부 결정 |
| 완료 조건 | 한 번 실행하면 무엇이 나와야 끝인가 | 이번 주 마감 표가 온다 | 새 공고와 맞는 정도·근거가 온다 |
| 결과를 받는 곳 | 어디로 오는가 | Slack DM | 메일 |

## 1-2. 일 사이의 연결 (선택)

일을 엮으면 쓴다. 엮지 않으면 비운다.

| 칸 | 쓸 것 | 예 |
|---|---|---|
| 어느 일의 무엇이 | 보내는 쪽 | 일 2에서 지원하기로 고른 공고의 마감 |
| 어느 일로 가는가 | 받는 쪽 | 일 1의 마감 목록(`data/마감.json`) |
| 연결을 맡은 것 | 코드, 에이전트, 사람 | 코드 |

## 2. 하루 사용 장면

시간 순서로 쓴다. 언제 무엇이 시작되는지, 결과를 받는 곳에 무엇이 오는지, 내가 무엇을 누르는지 쓴다.

예: 07:30 마감 브리핑 시작 → Slack에 이번 주 마감 4건 → 08:00 공고 브리핑 시작 → 메일에 공고 5건 → 지원할 2건 승인 → 그 2건의 마감이 마감 목록에 더해진다

## 3. 기능 지도

맡길 일마다 무엇으로 각 기능을 채우는지 쓴다. 도구는 자유다. 필수 기능 5개는 일 전체에서 1번 이상 채운다. 빈칸이 있으면 그 기능을 어느 일에 넣을지 정한다. 기능의 뜻은 [최종결과물.md](최종결과물.md)의 "꼭 들어갈 기능"에 있다.

| 구분 | 기능 | 예: 일 1 | 예: 일 2 | Kiro Crew로 하면 |
|---|---|---|---|---|
| | 쓰는 도구와 고른 까닭 | Kiro Crew. 9주차에 써 봤다 | Kiro Crew | |
| | 에이전트 | 마감 비서 | 공고 비서 | 에이전트 |
| 필수 | 근거 자료 | 강의계획서 | 내 경험 정리 | 지식 |
| 필수 | 직접 쓴 코드 | 마감 형식 검사 스크립트 | 공고 수집 스크립트 | 스킬의 `scripts/` |
| 필수 | 정해진 때의 자동 실행 | 매일 07:30 | 매일 08:00 | 스케줄 |
| 필수 | 사람의 결정 | 모호한 마감 확정 | 지원할 공고 선택 | Slack 선택 버튼 |
| 필수 | 결과를 받는 곳 | Slack DM | 메일 | Slack DM |
| 권장 | 재사용하는 절차 | 마감 뽑기 스킬 | 공고 비교 스킬 | 스킬 |
| 권장 | 막는 규칙 | 마감 목록 삭제 막기 | 외부로 보내기 막기 | 가드레일 |

"사람의 결정"에는 왜 자동으로 하면 안 되는지도 쓴다. 세 기준 가운데 하나 이상으로 쓴다: 되돌리기 어렵다, 책임이 따른다, 기준이 모호하다.

## 4. 처리 흐름

일마다 입력부터 출력까지 단계를 쓴다. 단계마다 담당을 정한다: 코드, 에이전트, 사람. 모든 단계를 자동으로 만들지 않아도 된다. 사람이 하는 단계에는 쓰는 도구를 함께 쓴다(예: Aside로 공고를 보고 결과를 `inbox/`에 저장한다).

| 일 | 단계 | 하는 일 | 담당 | 입력 → 출력 |
|---|---|---|---|---|
| 2 | 1 | 공고 수집 | 코드 | 검색어 → 공고 목록 JSON |
| 2 | 2 | 내 조건과 비교 | 에이전트 | 공고 목록, 이력서(근거 자료) → 맞는 정도와 근거 |
| 2 | 3 | 지원 여부 결정 | 사람 | 비교 결과 → 승인한 공고 |
| 2→1 | 4 | 승인한 공고의 마감을 마감 목록에 더하기 | 코드 | 승인한 공고 → `data/마감.json` |

## 5. 검증 방법

| 일 | 형식 검사 (코드로 확인할 것) | 내용 검사 (원본과 대조할 것) | 틀렸을 때 |
|---|---|---|---|
| 2 | 공고마다 회사·마감일·링크가 있는가 | 마감일이 공고 원문과 같은가 | 검사 실패를 알리고 그 공고는 빼고 보낸다 |

## 6. 이번에 만들지 않는 것

자른 기능을 목록으로 쓴다. 자른 까닭을 함께 쓴다.

## 7. 일정과 확인 지점

| 시점 | 끝나 있어야 할 것 |
|---|---|
| 11주차 끝 | 일마다 핵심 부품(코드, 절차, 근거 자료)이 손으로 실행해서 한 번 돈다 |
| 12주차 끝 | 일마다 처음부터 끝까지 한 번 돌고, 결과를 받는다. 결정을 한 번 한다 |
| 13주차 시작 | 매일 사용을 시작한다 |
| 14주차 끝 | 기준 수치를 채우고 발표 자료 초안을 만든다 |

## 8. 사용 계획 (13~14주차)

| 칸 | 쓸 것 |
|---|---|
| 실행 시각 | 일마다. 노트북과 도구가 켜져 있는 시각 |
| 기록 방법 | 일지와 변경 기록을 언제 쓰는가 |
| 놓친 날 | 실행되지 않은 날을 어떻게 기록하는가 |

## 9. 위험

| 칸 | 쓸 것 |
|---|---|
| 2주 안에 안 쓰게 될 이유 | 한 가지 이상 |
| 막힐 것 같은 곳 | 자료 접근, 코드 구현, 시간 가운데 무엇인가 |

## 10. 레포에 넣지 않을 것

토큰, 비밀번호, 개인 정보처럼 레포에 넣지 않을 것을 쓴다. 그 값을 대신 어디에 두는지도 쓴다.
