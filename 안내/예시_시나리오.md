# 예시 시나리오

세 시나리오는 출발점이다. 그대로 해도 되고, 바꾸거나 섞어도 된다. 내 일로 새로 정해도 된다.

예는 Kiro Crew와 Slack으로 적었다. 같은 기능을 다른 도구로 채워도 되고, 결과를 Slack이 아닌 곳으로 받아도 된다.

맡길 일은 2개 이상이다. 시나리오 2개를 골라도 되고, 한 시나리오와 내 일을 섞어도 된다. 시나리오의 "쓰는 기능" 표는 계획서 3번 기능 지도를 채울 때 예로 쓴다. 두 시나리오를 엮는 예는 맨 아래에 있다.

| | ① 수업·과제 마감 관리 | ② 채용 공고 점검 | ③ 관심 분야 리서치 브리핑 |
|---|---|---|---|
| 자료가 들어오는 길 | 내가 손으로 넣는다 | 코드가 공개 웹 페이지에서 가져온다 | 코드가 공개 API에서 가져온다 |
| 중심 기능 | 지식, 스킬, 사람의 확인 | 커스텀 도구, 비교, 승인 | 동적 워크플로우 |
| 어려운 곳 | 공지 형식이 제각각이다 | 사이트 구조와 이용 조건 | 요약이 좋은지 판정하기 |

세 시나리오에 함께 적용하는 규칙:

- 이미 처리한 것의 목록은 파일(`data/`)로 남긴다. 스케줄의 대화 맥락에 기대지 않는다.
- Slack에서는 선택 버튼으로 결정한다. 대시보드의 질문 카드는 Slack에 나오지 않는다.
- 코드가 할 수 있는 일(가져오기, 중복 빼기, 형식 검사)은 코드에 맡긴다. 판단이 필요한 일만 에이전트에게 맡긴다.
- 모든 단계를 자동으로 만들지 않아도 된다. 자료 모으기는 Aside 같은 AI 브라우저로 하고, 결과를 내가 복사해서 `inbox/`에 파일로 저장해도 된다. 그 단계의 담당은 "사람"으로 적는다.

## ① 수업·과제 마감 관리

강의계획서와 수업 공지에서 마감을 뽑는다. 매일 아침 이번 주 할 일을 Slack으로 받는다.

### 미리 모을 자료

| 자료 | 쓰는 곳 |
|---|---|
| 이번 학기 강의계획서 (과목마다 1개) | 지식. 과목별 평가와 제출 규칙의 근거 |
| 지난 공지 5건 이상 (형식이 다른 것) | 스킬을 시험할 입력 |

### 주기적으로 확보할 자료

| 자료 | 확보하는 방법 |
|---|---|
| 새 공지 | 학교 시스템은 로그인해야 보인다. 그래서 받은 공지를 `inbox/`에 붙여 넣는다. 하루 1분이면 된다 |
| 확정한 마감 목록 | 에이전트가 `data/마감.json`에 쌓는다 |

### 쓰는 기능

| 기능 | 쓰는 곳 | 배운 주차 |
|---|---|---|
| 지식 | 강의계획서를 등록한다 | 4 |
| 스킬 | 공지에서 과목·과제·마감·제출 방법을 뽑는 절차와 출력 형식 | 3 |
| 커스텀 도구 | 뽑은 마감의 형식 검사, 중복 빼기, 남은 날 계산 스크립트 | 3 |
| 스케줄 | 매일 07:30 이번 주 할 일 | 6 |
| 사람의 결정 | "다음 수업 전까지"처럼 모호한 마감을 선택 버튼으로 확정한다 | 6~7 |
| 가드레일 | `data/마감.json`을 지우는 명령을 막는다 | 6~7 |
| Slack | 아침 브리핑, 마감 하루 전 알림 | 9 |

### 과정

| 단계 | 하는 일 | 담당 |
|---|---|---|
| 1 | 07:30에 스케줄이 시작한다 | 스케줄 |
| 2 | `inbox/`의 새 공지에서 마감 후보를 뽑는다 | 에이전트(스킬) |
| 3 | 형식을 검사하고, 이미 있는 마감과 겹치는 것을 뺀다 | 코드 |
| 4 | 모호한 마감을 Slack 선택 버튼으로 묻는다 | 사람 |
| 5 | 확정한 마감을 `data/마감.json`에 더하고, 이번 주 할 일을 Slack으로 보낸다 | 에이전트 |
| 6 | 처리한 공지를 `inbox/처리됨/`으로 옮긴다 | 코드 |

### 쓰다 보면 고칠 것의 예

- 같은 과제가 두 공지에 나와서 두 번 잡힌다. 그래서 중복을 가리는 기준을 고친다.
- 강의계획서와 공지의 마감이 다르다. 그래서 어느 쪽을 따를지 묻는 결정 지점을 더한다.

### 공개 레포 주의

공지에 다른 학생의 이름이 있으면 `inbox/`를 `.gitignore`에 넣는다.

## ② 채용 공고 점검

관심 직무의 공고를 매일 모아 내 경험과 비교한다. 지원할 공고는 내가 고른다.

### 미리 모을 자료

| 자료 | 쓰는 곳 |
|---|---|
| 내 경험 정리: 수업 프로젝트, 기술, 자격 (연락처 같은 개인 정보는 뺀다) | 지식. 공고와 비교하는 근거 |
| 관심 직무, 지역, 제외 조건 | `조건.md`. 수집과 비교의 기준 |

### 주기적으로 확보할 자료

| 자료 | 확보하는 방법 |
|---|---|
| 새 공고 | 방법 A: 공개 목록 페이지나 RSS가 있는 사이트 1~2곳에서 수집 스크립트로 가져온다. 로그인해야 보이는 페이지와 이용 약관이 자동 수집을 막는 사이트는 스크립트로 가져오지 않는다. 방법 B: Aside 같은 AI 브라우저로 공고를 모으고, 결과를 `inbox/`에 파일로 저장한다 |
| 이미 본 공고 목록 | `data/본_공고.json`. 새 공고만 고르는 기준이다 |

### 쓰는 기능

| 기능 | 쓰는 곳 | 배운 주차 |
|---|---|---|
| 커스텀 도구 | 방법 A: 공고 수집 스크립트(검색어 → 회사·직무·마감·링크 JSON). 방법 B: `inbox/`의 파일을 같은 JSON으로 바꾸고 검사하는 스크립트 | 3 |
| 지식 | 내 경험 정리를 등록한다 | 4 |
| 스킬 | 공고와 내 경험을 비교하는 절차와 출력 형식 | 3 |
| 서브에이전트 | 공고가 많으면 공고별 비교를 나눠 맡긴다 (선택) | 6~7 |
| 스케줄 | 매일 08:00 | 6 |
| 사람의 결정 | 지원할 공고를 고른다 | 6~7 |
| 가드레일 | 지원서 제출처럼 외부로 보내는 동작을 막는다. 에이전트는 준비까지만 한다 | 6~7 |
| Slack | 브리핑과 선택 버튼 | 9 |

### 과정

| 단계 | 하는 일 | 담당 |
|---|---|---|
| 1 | 08:00에 스케줄이 시작한다 | 스케줄 |
| 2 | 새 공고를 가져온다 | 코드(방법 A) 또는 사람(방법 B, AI 브라우저) |
| 3 | 이미 본 공고를 뺀다 | 코드 |
| 4 | 공고마다 내 경험과 비교하고 근거를 붙인다 | 에이전트(지식, 스킬) |
| 5 | 마감일과 링크가 원문과 같은지 검사한다 | 코드 |
| 6 | 맞는 공고 5건을 선택 버튼과 함께 Slack으로 보낸다 | 에이전트 |
| 7 | 고른 공고만 지원 준비 메모를 만든다 | 에이전트 |

### 쓰다 보면 고칠 것의 예

- 사이트 구조가 바뀌어 수집이 0건이 된다. 그래서 0건이면 실패로 알리게 고친다.
- 비교 결과가 매일 비슷하다. 그래서 제외 조건을 더한다.

## ③ 관심 분야 리서치 브리핑

관심 주제의 새 논문이나 글을 매일 모아 요약한다. 내가 고른 것만 깊이 읽기 노트로 남긴다.

### 미리 모을 자료

| 자료 | 쓰는 곳 |
|---|---|
| 관심 키워드 3~5개 | 수집의 기준 |
| 이미 읽은 자료 목록과 메모 | 지식. 새 자료와 견주는 기준 |
| 좋은 요약의 예 1~2개 | 스킬의 출력 형식 |

### 주기적으로 확보할 자료

| 자료 | 확보하는 방법 |
|---|---|
| 새 자료 | arXiv API처럼 공개 API나 RSS가 있는 출처를 쓴다. API가 없는 출처는 AI 브라우저로 모아 `inbox/`에 저장해도 된다 |
| 이미 읽은 목록 | `data/읽음.json` |
| 깊이 읽기 노트 | 고른 자료의 노트가 지식 폴더에 쌓인다. 다음 날 비교에 쓰인다 |

### 쓰는 기능

| 기능 | 쓰는 곳 | 배운 주차 |
|---|---|---|
| 커스텀 도구 | API 조회 스크립트: 키워드 → 제목·초록·링크 JSON | 3 |
| 동적 워크플로우 | 두 관점 분석(내 관심과의 관련, 방법의 새로움) → 검토 → 요약 | 9 |
| 지식 | 읽은 자료와 깊이 읽기 노트 | 4 |
| 스케줄 | 매일 아침 | 6 |
| 사람의 결정 | 깊이 읽을 1~2편을 고른다. 키워드를 고친다 | 6~7 |
| 가드레일 | `data/읽음.json`을 지우거나 덮어쓰는 명령을 막는다 | 6~7 |
| Slack | 브리핑과 선택 버튼 | 9 |

### 과정

| 단계 | 하는 일 | 담당 |
|---|---|---|
| 1 | 아침에 스케줄이 시작한다 | 스케줄 |
| 2 | 키워드로 새 자료를 조회한다 | 코드 |
| 3 | 이미 읽은 자료를 뺀다 | 코드 |
| 4 | 두 관점으로 분석하고, 검토하고, 요약한다 | 에이전트(동적 워크플로우) |
| 5 | 요약을 선택 버튼과 함께 Slack으로 보낸다 | 에이전트 |
| 6 | 고른 자료의 깊이 읽기 노트를 만든다 | 에이전트 |

스케줄에서 동적 워크플로우를 바로 부를 수 있는지는 9주차에 확인한다. 부를 수 없으면 4번 단계는 에이전트가 단계별로 한다.

### 쓰다 보면 고칠 것의 예

- 관련 없는 자료가 많다. 그래서 키워드와 제외어를 고친다.
- 요약이 초록을 다시 쓴 수준이다. 그래서 스킬의 출력 형식에 "내 관심과의 관련" 칸을 더한다.

## 고르기 전에 확인할 것

| 질문 | 아니면 |
|---|---|
| 13~14주차에 매일 쓸 이유가 있는가 | 주제를 바꾼다 |
| 자료를 매일 확보할 수 있는가 (로그인, 이용 약관) | 자료가 들어오는 길을 바꾼다 |
| 사람이 결정해야 하는 자리가 있는가 | 결정 지점을 찾는다 |
| 코드가 들어갈 자리가 있는가 | 커스텀 도구가 될 일을 찾는다 |
| 12주차 끝까지 처음부터 끝까지 한 번 돌 크기인가 | 기능을 자른다 |

## 엮는 예: ② 채용 공고 → ① 마감 관리

두 일을 따로 만든 뒤 한 곳에서 잇는다.

| 칸 | 내용 |
|---|---|
| 보내는 일 | ② 채용 공고 점검: 지원하기로 고른 공고 |
| 보내는 것 | 회사, 직무, 지원 마감일, 링크 |
| 받는 일 | ① 마감 관리: `data/마감.json` |
| 연결을 맡은 것 | 코드. 승인한 공고를 마감 형식으로 바꿔 목록에 더한다 |
| 확인하는 방법 | 다음 날 아침 마감 브리핑에 그 공고의 지원 마감이 나온다 |

연결은 사람의 결정 다음에 둔다. 그래서 내가 고른 공고만 마감 목록에 들어간다. 연결의 형식과 돈 기록은 `구성/연결.md`에 쓴다.
